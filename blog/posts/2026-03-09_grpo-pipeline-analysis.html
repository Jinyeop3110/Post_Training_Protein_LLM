This post documents the complete GRPO training pipeline in src/training/grpo_trainer.py (1,980 lines). The implementation is a custom PyTorch GRPO trainer that handles generation, reward computation, advantage estimation, and policy gradient updates—all without relying on external RL frameworks.

1. Custom GRPO Implementation (No veRL)

What We Actually Use

The entire GRPO pipeline is custom PyTorch + transformers + PEFT. Despite the config declaring framework: verl, there are zero imports from veRL in the codebase. The implementation builds on:

DependencyWhat It ProvidesLines
torchCore training loop, autograd, distributedThroughout
transformersModel loading, tokenization, .generate()33–44
peftLoRA adapter loading and application46–56
torch.distributedNCCL process group, all-reduce258–277
torch.distributed._composable.fsdpFSDP2 composable API72–77, 279–343

What veRL Would Provide (But We Don't Use)

veRL (Volcano Engine RL) is a distributed RL framework that would provide:

  • Actor-critic separation: Runs policy and critic models on different GPU groups
  • vLLM rollout engine: Fast generation with PagedAttention, continuous batching
  • Ray-based orchestration: Distributed scheduling across nodes
  • FSDP/Megatron integration: Automatic model sharding during training

Instead, our implementation handles all of this in a single GRPOTrainer class (grpo_trainer.py:142–1838), which is simpler but less optimized for large-scale distributed training.

TRL Import: Present But Dead

# grpo_trainer.py:58-63

2. Multi-GPU Training Strategy

FSDP2 Composable API

The GRPO trainer uses FSDP2 (PyTorch 2.4+ composable API), not the older FSDP1 wrapper. This is applied in _apply_fsdp() (grpo_trainer.py:279–343):

# grpo_trainer.py:296-330 — FSDP2 sharding
mesh = DeviceMesh("cuda", list(range(self.world_size)))
mp_policy = MixedPrecisionPolicy(
    param_dtype=torch.bfloat16,
    reduce_dtype=torch.float32,
)

# Wrap each decoder layer individually
for layer in base_model.model.layers:
    fully_shard(layer, mesh=mesh, mp_policy=mp_policy,
                reshard_after_forward=False)  # SHARD_GRAD_OP mode
# Wrap root model
fully_shard(base_model, mesh=mesh, mp_policy=mp_policy)
reshard_after_forward=False This is equivalent to FSDP1's SHARD_GRAD_OP strategy: parameters are gathered for forward and kept unsharded until after backward. This uses more memory than full sharding but avoids a second all-gather during backward.

Sharding Plan

ComponentStrategyWhy
Qwen3-8B LLM FSDP2 (per-layer sharding) ~16 GB → ~2 GB/GPU
ESM-3 encoder Replicated (excluded from FSDP) Frozen, fp32, ~1.2 GB — small enough to replicate
AttentionPooling + MLPProjector Replicated (manual gradient sync) ~30M params — too small for FSDP overhead
LoRA adapters Inside FSDP-wrapped layers ~2M params, live on the base model layers

embed_tokens Cache

Before FSDP shards the model, embed_tokens weights are cloned into a cache (grpo_trainer.py:312–318):

# Cache embed_tokens BEFORE FSDP shards the model
embed_weight = base_model.get_input_embeddings().weight.data.clone()
self.protein_llm._fsdp_embed_cache = embed_weight

After FSDP sharding, calling embed_tokens directly on sharded parameters produces garbage. ProteinLLM.prepare_inputs() uses this cache to correctly embed text tokens alongside protein prefix embeddings.

Manual Gradient Sync for Multimodal Params

Since pooling and projector are NOT FSDP-wrapped, their gradients need explicit all-reduce (grpo_trainer.py:1248–1263):

# grpo_trainer.py:1248-1263
def _sync_multimodal_gradients(self):
    if not dist.is_initialized() or dist.get_world_size() <= 1:
        return
    if self.protein_llm is None:
        return
    for module in [self.protein_llm.pooling, self.protein_llm.projector]:
        if module is not None:
            for p in module.parameters():
                if p.requires_grad and p.grad is not None:
                    dist.all_reduce(p.grad, op=dist.ReduceOp.AVG)

This is called after gradient accumulation completes, just before the optimizer step (grpo_trainer.py:1479).

Separate Gradient Clipping

FSDP and non-FSDP parameters require different clipping APIs (grpo_trainer.py:1482–1519):

if self.use_fsdp:
    # FSDP-aware clip for LLM (uses FSDP's clip_grad_norm_)
    base.clip_grad_norm_(max_grad_norm)
    # Standard clip for multimodal params (NOT FSDP-wrapped)
    torch.nn.utils.clip_grad_norm_(mm_params, max_grad_norm)
else:
    # Single clip for all params
    torch.nn.utils.clip_grad_norm_(all_params, max_grad_norm)

Distributed Sampling

Multi-GPU uses DistributedSampler with epoch-synced shuffling (grpo_trainer.py:1431–1457):

if self.world_size > 1:
    sampler = DistributedSampler(self.train_dataset, shuffle=True)
    # ...
for epoch in range(num_epochs):
    if sampler is not None:
        sampler.set_epoch(epoch)  # Ensures different shuffle per epoch

3. GRPO Algorithm Details

The algorithm follows the DeepSeekMath GRPO paper with DAPO and Dr. GRPO improvements. The core loop lives in _training_step() (grpo_trainer.py:1265–1398).

Step 1: Generation Phase (no_grad)

_generate_completions() (grpo_trainer.py:915–1027) generates group_size (8) completions per prompt. All completions for a single prompt are batched into one .generate() call:

# For each prompt, generate group_size completions in one batch
batch_proteins = [protein_seq] * num_completions
batch_prompts = [prompt] * num_completions

with torch.no_grad():
    texts, token_ids, input_len = self.protein_llm.generate(
        protein_sequences=batch_proteins,
        prompt=batch_prompts,
        return_token_ids=True,
        **gen_kwargs,
    )

For text-only prompts, it falls back to self.model.generate() with repeated input_ids (grpo_trainer.py:976–1013).

Step 2: Reward Computation

_compute_rewards() (grpo_trainer.py:1133–1181) calls the task-specific reward function. Ground truth extraction is task-aware:

TaskGround Truth SourceReward Function
GO predictionbatch["response"]compute_go_reward (F1 score)
Stability/ddGmetadata.ddGcompute_stability_reward (Gaussian decay)
ESMFold/Structuremetadata.plddt as JSONcompute_esmfold_reward (3-component)
ProteinLM Benchmetadata.answercompute_proteinlm_bench_reward (binary)
PPIbatch["response"]compute_ppi_reward (binary)

For ESMFold, the reward function checks if the ground truth is a JSON string with pre-computed metrics. If so, it uses those directly (instant). Otherwise, it falls through to the live ESMFold path (rewards.py:396–412).

Step 3: Advantage Computation

_compute_advantages() (grpo_trainer.py:1183–1206) computes group-relative advantages:

# grpo_trainer.py:1196-1206
group_mean = rewards.mean(dim=1, keepdim=True)
group_std = rewards.std(dim=1, keepdim=True)

advantages = rewards - group_mean   # A_i = r_i - mean(r_group)

# Normalize if configured (NOT used — Dr. GRPO variant)
if self.grpo_config["normalize_advantages"]:
    advantages = advantages / (group_std + 1e-8)
DAPO + Dr. GRPO Configuration Both configs set use_kl_penalty: false (DAPO improvement) and normalize_advantages: false (Dr. GRPO improvement). This means: no KL constraint against a reference model, and raw (unnormalized) advantages. The advantage for a completion is simply how much better or worse its reward is compared to the group mean.

Step 4: Differentiable Log Prob Re-computation

This is the critical step. Log probs are re-computed with gradients via _compute_policy_log_probs() (grpo_trainer.py:1063–1131). See Section 4 for details.

Step 5: Policy Gradient Loss

# grpo_trainer.py:1371-1372
pg_loss = -(advantages * log_probs).mean()   # REINFORCE with group baseline

This is the standard REINFORCE objective: increase log probability of completions with positive advantages (better than group average), decrease for negative advantages.

4. Gradient Flow Fix

The GRPO pipeline has two separate log-probability computation functions. Understanding why is critical to understanding the gradient flow.

The Problem

In the original design, log probabilities were computed inside torch.no_grad() during generation. Using these for the policy loss would produce zero gradients—the model would never learn.

The Fix: Two Functions

Function Gradients? Purpose Lines
_compute_sequence_log_prob() NO (torch.no_grad()) Reference model log probs for KL penalty (currently dead code) 1029–1061
_compute_policy_log_probs() YES (with grad) Policy log probs for REINFORCE loss — this is the differentiable forward pass 1063–1131

_compute_policy_log_probs() in Detail

This function performs a full forward pass WITH gradients through the entire multimodal pipeline:

# grpo_trainer.py:1063-1131 — Differentiable forward pass
def _compute_policy_log_probs(self, prompt_ids, generated_ids, protein_sequence=None):
    full_ids = torch.cat([prompt_ids, generated_ids], dim=1)
    attention_mask = torch.ones_like(full_ids)

    if self.protein_llm is not None and protein_sequence is not None:
        # Multimodal: ESM-3 encode → pooling → projector → LLM
        prepared = self.protein_llm.prepare_inputs(
            protein_sequences=[protein_sequence],
            text_input_ids=full_ids,
            text_attention_mask=attention_mask,
        )
        outputs = self.protein_llm.llm(
            inputs_embeds=prepared["inputs_embeds"],  # gradient flows through here
            attention_mask=prepared["attention_mask"],
            position_ids=prepared["position_ids"],
            return_dict=True,
        )
        # Account for protein prefix tokens in logit positions
        num_prefix = self.protein_llm.num_prefix_tokens
        logits = outputs.logits[:, num_prefix + prompt_length - 1:-1, :]
    else:
        outputs = self.model(full_ids, return_dict=True)
        logits = outputs.logits[:, prompt_length - 1:-1, :]

    # Log softmax → gather → sum
    log_probs = F.log_softmax(logits, dim=-1)
    token_log_probs = torch.gather(log_probs, dim=-1, index=target_ids.unsqueeze(-1))
    pad_mask = (target_ids != self.tokenizer.pad_token_id).float()
    return (token_log_probs * pad_mask).sum()

The key insight: by passing through prepare_inputs() which runs the encoder→pooling→projector pipeline, gradients flow through the entire multimodal stack, not just the LLM. This is what allows GRPO to update the projector and pooling weights.

_compute_sequence_log_prob() is Dead Code

_compute_sequence_log_prob() (grpo_trainer.py:1029–1061) runs under torch.no_grad() and is never called anywhere in the codebase. It was intended for computing reference model log probs for KL penalty, but since use_kl_penalty: false, it's unused. It could be removed without impact.

5. Wandb Logging

What's Logged

Logging happens at each optimizer step (every grad_accum_steps micro-batches), controlled by logging_steps (grpo_trainer.py:1527–1545):

MetricDescription
lossTotal loss (pg_loss + kl_penalty)
pg_lossPolicy gradient loss: -(advantages * log_probs).mean()
kl_penaltyKL divergence (always 0.0 with DAPO)
mean_rewardAverage reward across all completions in the batch
max_reward, min_rewardReward range
reward_stdReward standard deviation
lrCurrent learning rate (from scheduler)
reward/{metric}Per-task supplementary metrics (e.g., reward/f1, reward/mae)
eval_mean_rewardEvaluation reward (logged at eval_steps)

What's Missing

Logging Gaps
  • Generated sample text: No completions are logged to wandb. Adding a few text samples per eval step would help debug reward function behavior.
  • Gradient norms: No tracking of LLM vs multimodal gradient magnitudes. Important for detecting the NaN issues we've seen in SFT.
  • Per-group reward distributions: Only batch-level stats are logged. Per-prompt group distributions would reveal if GRPO is exploring effectively.
  • Advantage statistics: Mean/std of advantages not tracked. Useful for detecting collapsed advantages (all rewards equal → zero learning signal).
  • Token counts: No logging of generated token lengths. Important for detecting degenerate outputs (empty or repeated tokens).

6. Config Issues

The GRPO config (configs/training/grpo.yaml) has several vestigial or misleading fields:

Issue 1: framework: verl (Vestigial)

# configs/training/grpo.yaml:1-2
method: grpo
framework: verl  # ← VESTIGIAL: zero veRL imports in codebase

This field is never read by any code. It suggests veRL was initially planned but the custom implementation was used instead. Should be removed or changed to framework: custom.

Issue 2: rollout.engine: vllm (Misleading)

# configs/training/grpo.yaml:39-43
rollout:
  engine: vllm  # ← MISLEADING: actually uses HF .generate()
  temperature: 1.0
  top_p: 0.95
  max_tokens: 512

The engine field is never read. Generation always uses model.generate() (HuggingFace) or protein_llm.generate() (grpo_trainer.py:962–968). vLLM would provide significantly faster generation via PagedAttention, but it's not integrated.

Issue 3: clip_range: 0.2 (Unused)

# grpo_trainer.py:129 — read from config
"clip_range": grpo_cfg.get("clip_range", 0.2),

The clip_range parameter is loaded into grpo_config and saved to training_args.json, but it's never used in any computation. In PPO, clip_range limits the policy ratio min(ratio * A, clip(ratio, 1-e, 1+e) * A). GRPO doesn't use policy ratio clipping—it uses raw REINFORCE with group baselines. This parameter is a leftover from a PPO-style design.

7. Summary and Recommendations

Architecture Summary

What Works Well
  • Custom GRPO with verifiable rewards—no reward model overhead
  • FSDP2 with per-layer sharding enables 8B models on 4×L40S
  • embed_tokens cache solves FSDP sharding corruption for multimodal
  • Separate gradient clipping for FSDP vs multimodal params
  • Gradient flow through full encoder→pooling→projector→LLM pipeline
  • Task-aware ground truth extraction handles all five reward types
Known Issues / Tech Debt
  • Vestigial config: framework: verl, rollout.engine: vllm, clip_range
  • _compute_sequence_log_prob() is dead code
  • run_grpo_with_trl() is a stub (NotImplementedError)
  • Missing wandb logging: no sample text, gradient norms, or advantage stats
  • Generation is sequential per-prompt (no batched multi-prompt generation)
  • KL penalty path exists but is untested (no reference model created when disabled)

Potential Improvements

  1. Clean up config: Remove vestigial fields (framework, rollout.engine, clip_range)
  2. Remove dead code: _compute_sequence_log_prob(), run_grpo_with_trl(), create_reward_dataset()
  3. Add wandb sample logging: Log 3–5 generated completions per eval step with rewards
  4. Batch generation: Generate for multiple prompts simultaneously instead of per-prompt loops
  5. vLLM integration: Replace HF .generate() with vLLM for 2–5x faster rollouts
  6. Gradient norm tracking: Log LLM vs multimodal gradient norms for debugging
